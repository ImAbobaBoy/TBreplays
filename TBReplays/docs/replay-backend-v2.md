# TBReplays: backend и JSON v2

Патч рассчитан на backend из TBReplays_28.09.zip. Применяется из папки,
в которой находятся TBReplays.sln и подпапка TBReplays с TBReplays.csproj.
Frontend в этот патч не входит: для работы с готовой статистикой его следует
подключить к новому /presentation. Старый /parse-result сохранён.

## Установка

```bash
git apply --check TBReplays_backend_v2.patch
git apply TBReplays_backend_v2.patch
dotnet build TBReplays.sln
```

Если Git нормализовал исходные CRLF при клонировании, а обычный `--check`
сообщает о несовпадении строк, используйте `git apply --ignore-space-change --check`
и затем `git apply --ignore-space-change` с тем же файлом патча.

Архив TBReplays_xml_26.4.zip содержит:

- `runtime/TBReplays/ClientGameData/26.4.0_ruby/...` — исходные XML в DVPL и локализацию.
  Скопируйте содержимое папки `runtime` рядом с TBReplays.sln с сохранением вложенности.
  Получится `TBReplays/ClientGameData/26.4.0_ruby/XML/item_defs/vehicles/...`.
- `readable-xml/...` — те же XML в распакованном виде и ru.yaml для просмотра.
  Загрузчик использует `.xml.dvpl`, поэтому распакованные копии не нужно подменять
  вместо runtime-файлов или переименовывать в `.dvpl`.
- `manifest.txt` — пути и SHA-256 исходных файлов.

Это справочники 26.4 из предоставленного проекта, не новые справочники 26.8.
Не переименовывайте каталог в 26.8: несовпадение версии корректно отражается в warnings.
HP и фактические таймеры эффектов берутся из реплея, а не из старых XML.
Если эти runtime-файлы уже есть в проекте, повторное копирование не требуется.

После обновления перезапустите backend и повторно импортируйте реплеи:
уже сохранённые `parse_result.json` автоматически не пересчитываются.
`/presentation` для старого JSON возвращает HTTP 409 с просьбой повторного импорта.

## Что изменилось

- HP: прочитаны current HP и max HP из снимков появления танка. `initialHealth`
  теперь означает начальное HP, а не HP при первом засвете. Первое наблюдение
  вынесено в `firstObservedHealth` / `firstObservedHealthTime`.
- Приоритет начального HP: max HP снимка → положительная сумма итогового HP и
  полученного урона. Нулевые protobuf-поля учитываются как нули. Отрицательные
  значения HP уничтоженного танка нормализуются в 0. Нулевую сумму не выдаём
  за достоверное начальное HP: в ex2 обнаружен такой случай самоуничтожения.
- Каталожное HP и максимальное наблюдаемое HP больше не подменяют точное
  начальное HP. При нехватке данных возвращается null.
- Снаряжение: отдельно разобраны subtype 0 канала 32 и массив extras в снимке.
  Профиль 26.4 использует ID uint8 и запись 14 байт, профиль 26.8 — uint16 и 15 байт.
  Модули subtype 1 не попадают в снаряжение. Учитываются timerStamp/duration.
- Сопоставление: runtime ID → атрибут index из common/vehicle.xml → определение
  consumables/provisions/optional_devices → русская локализация. Item ID и runtime ID
  сохраняются отдельно. isAbility отделяет механику танка от расходуемого снаряжения.
- Неизвестные состояния механик сохраняются. Например, состояние 11 брони Урана
  не приводит к потере снимка всего танка.
- Использования: активация и её cooldown считаются одним применением; повторный
  засвет не создаёт дубль. Активный эффект или cooldown при засвете может подтвердить
  пропущенное применение. Количество — минимально подтверждённое.
- Исход боя: победитель и код причины из итогов, проверка по событию завершения.
  Уничтожения читаются из глобального события арены, включая убийства вне видимости.
  Время последнего движения больше не объявляется временем смерти.
- Очки: сохраняются все обновления командного счёта и их порядок. Одновременные
  изменения объединяются в один кадр табло, без промежуточного ложного счёта.
- Итоги при отсутствии/повреждении battle_results.dat восстанавливаются из
  сжатого финального пакета. Pickle не исполняется, читается только ограниченная оболочка.
- Добавлены ограничения распаковки, проверки размеров, protobuf-varint и времени пакетов.

## API

Импорт остаётся прежним: `POST /api/replays/import`, multipart поле `files`.
Метаданные импорта и списка реплеев включают `schemaVersion`, `outcome`, `teams`.

Для нового интерфейса:

```http
GET /api/replays/{replayId}/presentation
```

| Поле | Назначение |
|---|---|
| schemaVersion | 2; старый JSON без поля читается как версия 1 |
| clientVersion / catalogVersion | Версии реплея и справочников |
| arenaUniqueId | Строка, без потери точности JavaScript Number |
| recorderEntityId / recorderTeamId | Автор записи и его команда; могут быть null |
| mapName / mapId / mapBinding | Карта и привязка к backend-карте |
| outcome | Победитель, причина, время события окончания, источник, согласованность |
| vehicles | Итоговая статистика по танкам, начальное/конечное HP, урон, снаряжение |
| teams | Готовые командные суммы, живые танки, уничтожения, итоговые очки |
| playback | Готовые состояния и сгруппированные данные воспроизведения |
| warnings | Недостаток данных, расхождения и непроверенные версии |

### Outcome

`winnerTeamId`: 1/2 — команда, 0 — ничья по итогам, null — неизвестно.
`status`: victory/draw/unknown. `finishReasonCode` всегда сохраняет код протокола.
Подтверждены `reason=annihilation` (код 1) и `reason=supremacy` (код 6).
Другие причины, включая ещё не проверенный захват базы, остаются `unknown`.
Для добавления точного кода захвата нужен реплей, действительно завершившийся захватом.
Нельзя определять причину победы только по наличию очков или числу убийств.

Если итог и событие завершения противоречат друг другу, приоритет у итогов,
`sourcesAgree=false`, в warnings фиксируется расхождение.

### Vehicles и teams

Для отрисовки идентификаторы, имя, страна, класс и уровень танка уже сопоставлены.
`initialHp`, `finalHp`, `damageDealt`, `damageReceived`, `isDestroyed` — итоговые данные.
`observedShots` — выстрелы, видимые в записи; `confirmedKills` — глобально подтверждённые
события уничтожения. Эти названия намеренно не обещают полноту там, где её нет.
`extras` содержит установленное снаряжение, амуницию, пассивные эффекты и механики:

- `extraId` — ID в потоке, `itemId` — ID предмета XML;
- `key`, `name`, `kind`, `icon` уже сопоставлены;
- `directUses`, `inferredUses`, `minimumUses` — посчитаны сервером;
- `usageMayBeIncomplete` — применений могло быть больше вне видимости;
- `icon` — ключ ресурса из XML, не URL изображения.

Неизвестные итоги и суммы с неизвестными слагаемыми возвращаются как null.
В командах `confirmedKills` и `aliveCount` имеют разный смысл: самоубийство
уменьшает живых, но не обязано приносить убийство сопернику.

### Playback: фронт выбирает кадр и рисует

Всё время в секундах относительно часов `data.replay`: `timeBasis=replaySeconds`.
Это не оставшееся время на игровом таймере. `startTime`/`endTime` задают диапазон.

`playback.vehicles[]` — готовые треки по entityId. В каждом:

- `movement`: отсортированные позиции/углы, segmentIndex;
- `turret`: отсортированные углы башни;
- `states`: полностью собранные состояния, один кадр на timestamp;
- `visibility`: интервалы видимости, выведенные из движения;
- `consumableUses`: уже очищенная от дублей история;
- `shots`: выстрелы данного танка.

При времени t выбирайте последний `states[i]` с `time <= t`:

- `health`, `healthFraction` — готовое HP и доля полоски;
- `isAlive`, `isVisible`, `healthIsLastKnown` — состояние и достоверность;
- `observedDamageReceived`, `confirmedKills` — готовые накопленные значения;
- `extras`, `modules` — состояние снаряжения/модулей на этот момент.

В extras состояние Activated означает наблюдаемый активный эффект; Cooldown —
перезарядку; Installed — последнее известное готовое состояние. После расчётного
окончания активной фазы без нового пакета используется UnknownAfterActivation,
после окончания cooldown — Installed с Inferred. После смерти — Cleanup.
Сервер добавляет кадры истечения таймеров; UI не должен сам менять состояние эффекта.
Для текста обратного отсчёта можно визуально вычитать t из stateEndTime.

Для плавного движения допустима интерполяция координат и углов между соседними
кадрами одного segmentIndex. Через разрыв сегмента интерполировать нельзя.
Это графическая задача; пересчитывать HP, победу, очки, убийства или применения
снаряжения на фронте не требуется.

`playback.scoreboard[]` уже содержит обе команды, HP, живых, убийства и очки.
Также выбирайте последний кадр `time <= t`. `hasUnobservedHealth` означает, что
командное HP включает последние известные значения невидимых живых танков.
Пропущенные изменения HP не приписываются придуманному времени попадания.

`playback.projectiles[]` содержит точки, сгруппированные по projectileId.

### Полный результат для диагностики

```http
GET /api/replays/{replayId}/parse-result
```

Сохраняет старые массивы и добавляет поля v2, `scoreEvents`, `killEvents`,
`battleResultFields` и `vehicleStatistics[].resultFields`. Недокументированным
полям protobuf не присваиваются выдуманные названия: номер/wireType сохраняются,
uint64 передаётся десятичной строкой, bytes — base64. Эти поля не нужны рендереру.

## Проверка

Добавлен проект TBReplays.Regression без отдельного тестового фреймворка:

```bash
dotnet run --project TBReplays.Regression -- TBReplays path/to/first.tbreplay path/to/second.tbreplay
```

Можно перечислить и файлы `TBReplays/ReplayFiles/*.tbreplay` отдельными аргументами.
Повреждение необязательных итогов, выпадение итогов, отрицательное HP, нулевые
поля, профили 26.4/26.8, неизвестные состояния механики, дубли, порядок и JSON
проверяются автоматически. Реплеи с личными данными в патч не включены.

Проверено 8 предоставленных реплеев, 1123 утверждений:

| openAXAX (26.8) | 14 | 31/31 | 2 / supremacy | 283 | 27 |
| ant200501 (26.8) | 14 | 21/21 | 1 / annihilation | 0 | 30 |

Все C# исходники backend скомпилированы Roslyn 4.11 с reference assemblies .NET 8
и зависимостями из исходного проекта. Регрессионная программа исполнена .NET 8.
Штатный dotnet build в рабочей среде недоступен из-за ошибки CLI при чтении
информации процесса; проверка выполнена прямым запуском компилятора.
